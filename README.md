# МТС EnergyTool — ИИ-консультант

Прототип ИИ-консультанта для сайта МТС EnergyTool (кейс МТС, True Tech Hack&Change 2026).
Консультант выясняет задачу клиента, подбирает продукт EnergyTool по базе знаний, объясняет
его простым языком, задаёт уточняющие вопросы, честно говорит, когда ответа в материалах нет,
и собирает заявку с резюме диалога для менеджера пресейла.

Один и тот же движок (`energy_rag.py`) отвечает и в веб-чате, и в конкурсном `solution.py`,
поэтому качество на лидерборде совпадает с тем, что видит пользователь.

---

## Запуск одной командой (Docker)

```bash
cp .env.example .env          # заполните LLM_BASE_URL и LLM_API_KEY (без них — демо-режим)
docker compose up --build
```

Откройте <http://localhost:8000/>. Порт — `8000`, проверка живости — `GET /api/health`.
История диалогов и заявки хранятся в volume `energytool-storage` (`/app/storage/app.db`).

### Проверка основного сценария

1. Откройте чат, напишите: «Хотим поставить солнечную станцию на склад в Краснодаре».
2. Ответьте на уточняющий вопрос (кровля, потребление), спросите о стоимости или окупаемости.
3. Консультант предложит оставить заявку → заполните ФИО, телефон, компанию (тестовые данные).
4. В ответ придёт номер заявки и резюме для менеджера.
5. Включите «Отладку»: видны время ответа, режим (LLM / демо), режим поиска
   (`bm25+bge-m3+rerank`) и фрагменты базы знаний с оценками.
6. «Новый диалог» сбрасывает контекст; прошлые сессии (в том числе без заявки) — в «Истории».

### Локально без Docker

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

## Архитектура

```
static/ (HTML+CSS+JS)        чат-виджет, отладка, история, форма заявки
        │ fetch /api/*
app/main.py (FastAPI)        REST: чат, сессии, заявки, health
app/consultant.py            состояние диалога: тема, слоты, момент заявки, быстрые ответы, демо-ответы
app/summary.py               резюме заявки для менеджера (LLM или шаблон)
app/store.py                 SQLite: sessions / messages / leads
        │
energy_rag.py                ЯДРО (общее с solution.py):
   ├─ KnowledgeBase          нарезка Markdown по заголовкам (раздел = фрагмент, длинные — по абзацам)
   ├─ BM25                   русский стемминг + словарь бытовых синонимов («симки» → SIM, «свет» → электроэнергия)
   ├─ bge-m3                 плотные эмбеддинги базы (кэш на диске) и запроса
   ├─ RRF                    слияние 4 ранжирований: BM25/dense × (последняя реплика / весь диалог)
   ├─ Qwen3 Reranker         переранжирование 24 кандидатов, в контекст идут лучшие 8
   ├─ Правила продукта       разделы «Факты, которые можно утверждать / Чего утверждать нельзя»
   │                         автоматически добавляются для продуктов из выдачи
   └─ Генерация              Qwen3 без режима размышлений, промпт консультанта + few-shot,
                             очистка Markdown, мягкий лимит ~150 слов
        │
data/knowledge-base/*.md     19 документов базы знаний
```

Каждый внешний вызов (эмбеддинги, реранкер, генерация) необязателен: при ошибке ответ
деградирует до BM25 и экстрактивного ответа, а не падает. Повторы — только ограниченные
(429/5xx/таймаут, до 3 попыток с паузой).

### Как консультант отвечает

- Первое предложение — прямой ответ («Да, …», «Нет, …», «Начать стоит с …»).
- Затем 1–3 предложения фактов из базы с оговорками, обычно 40–90 слов.
- В конце — один уточняющий вопрос для следующего шага (если нужен); то, что клиент уже сказал,
  не переспрашивается (слоты из `consultant.py` передаются в промпт).
- Нет ответа в базе или вопрос вне компетенции (настройка приборов, юридические заключения) —
  прямо говорит об этом и предлагает специалиста.
- Заявка: на 3-м ходу или по просьбе клиента предлагается оставить ФИО, телефон и компанию;
  если клиент не готов — не настаивает.

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `LLM_BASE_URL` / `OPENAI_BASE_URL` | — | OpenAI-совместимый прокси (генерация, эмбеддинги, реранкер) |
| `LLM_API_KEY` / `OPENAI_API_KEY` | — | ключ прокси |
| `LLM_MODEL` / `OPENAI_MODEL` / `GEN_MODEL` | `qwen/qwen3.8-27b` | модель генерации |
| `EMB_MODEL` | `BAAI/bge-m3` | модель эмбеддингов (`/embeddings`) |
| `RERANKER_MODEL` | `Qwen/Qwen3-Reranker-8B` | реранкер (`/rerank`) |
| `USE_EMBEDDINGS`, `USE_RERANKER` | `1` | отключить плотный поиск / реранкер |
| `TOP_K` | `8` | фрагментов базы в контексте ответа |
| `RERANKER_TOP_N` | `24` | кандидатов на реранкинг (не меньше 16) |
| `TEMPERATURE` | `0.1` | температура (ограничена сверху 0.3) |
| `MAX_TOKENS` | `700` | лимит ответа (в пределах 450–1200) |
| `LLM_TIMEOUT` | `60` | таймаут запроса, с |
| `MAX_WORKERS` | `8` | параллелизм `solution.py` |
| `TIME_BUDGET_SEC` | `1000` | общий дедлайн `solution.py` (лимит платформы 20 мин) |
| `KB_PATH` | `data/knowledge-base` | база знаний (папка или .zip) для веб-приложения |
| `DB_PATH` | `data/app.db` | SQLite с историей и заявками |
| `DATA_DIR` | `data` | где `solution.py` ищет `questions.csv` и `knowledge-base.zip` |

Внешний API — только OpenAI-совместимый прокси организаторов (модели Qwen3.8-27B, BAAI/bge-m3,
Qwen3 Reranker 8B). Ключи читаются из окружения; в коде, логах и репозитории их нет.
Без ключей веб-приложение работает в демо-режиме (BM25 + курируемые ответы `answers_core.py`).

Зависимости зафиксированы в `requirements.txt` (веб) и `requirements-solution.txt` (сабмит: только `httpx`).

## API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/health` | статус, фрагменты базы, режим LLM и поиска, статистика |
| `POST` | `/api/session/new` | новая сессия (сброс контекста) |
| `GET` | `/api/sessions` | последние диалоги |
| `GET` | `/api/sessions/{id}` | сообщения и заявка диалога |
| `POST` | `/api/chat` | `{session_id?, message}` → `answer`, `sources[]`, `lead`, `debug` |
| `POST` | `/api/lead` | `{session_id, name, phone, company, consent}` → номер заявки и резюме |

Встраивание в сайт: виджет — статический JS + REST, его можно подключить на сайт Energytool
iframe-ом или скриптом; заявки из таблицы `leads` передаются в CRM вебхуком (в прототипе
интеграции не требуются по условиям кейса).

## Конкурсный сабмит

```bash
python scripts/build_submission.py      # → submission.zip: solution.py, energy_rag.py, requirements.txt
```

Локальная проверка (нужны `data/questions.csv` и `data/knowledge-base.zip`):

```bash
DATA_DIR=data LLM_BASE_URL=... LLM_API_KEY=... python solution.py   # → submission.csv (id,answer)
```

Гарантии формата: заголовок `id,answer`, UTF-8, стандартное CSV-экранирование, ответ на каждый
ID без повторов, длина < 10 000 символов. Заглушка `submission.csv` пишется сразу при старте
и обновляется по ходу работы, поэтому даже при аварии файл валиден. Общий дедлайн 1000 с:
после него оставшиеся вопросы получают быстрый экстрактивный ответ.

Тесты без доступа к прокси: `tests/mock_proxy.py` имитирует `/chat/completions`, `/embeddings`,
`/rerank`, ответы с `<think>`, 429 и отказ от `chat_template_kwargs`.

## Данные и безопасность

- Материалы кейса используются только для задания. **Репозиторий должен оставаться приватным**
  (доступ — аккаунту жюри `hack-and-change-2026`): база знаний включена для запуска через Docker,
  публиковать её в открытом доступе нельзя.
- Только тестовые персональные данные; согласие на обработку обязательно в форме заявки.
- Секретов в репозитории нет, `.env` в `.gitignore`.

## Известные ограничения

- Качество ответов на платформе проверяется только сабмитами; локально без прокси доступен
  демо-режим и mock-тесты.
- SQLite и один процесс uvicorn — для прототипа; для продакшена нужны Postgres, очередь и
  внешнее хранилище сессий.
- Развитие: выгрузка заявок в CRM, авторизация менеджера, A/B-оценка ответов на реальных
  диалогах, автоматическая проверка ответов на запрещённые утверждения.
