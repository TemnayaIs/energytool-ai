# МТС EnergyTool — ИИ-консультант

Прототип ИИ-консультанта для сайта МТС EnergyTool: помогает клиенту сформулировать задачу,
подбирает продукт по базе знаний, задаёт уточняющие вопросы, честно отказывается отвечать вне
компетенции и собирает заявку с резюме диалога для менеджера.

Проект собран по кейсу и техническому регламенту хакатона МТС True Tech Hack&Change 2026.
Один и тот же RAG-движок используется в веб-прототипе и в конкурсном `solution.py`.

---

## Что умеет

- **Многошаговый диалог.** Консультант помнит контекст, извлекает параметры объекта
  (регион, мощность, потребление, кровля, количество приборов, ценовая категория, цели)
  и не спрашивает одно и то же дважды.
- **Пять направлений.** Облачный учёт электроэнергии, поиск коммерческих потерь,
  распознавание показаний по фото, солнечные станции под ключ, выход на оптовый рынок.
- **Ответы только по базе знаний.** Поиск BM25 + расширение запросов + профильные документы;
  при подключённой LLM — генерация строго по найденному контексту.
- **Корректный отказ.** Если данных в базе нет или вопрос вне компетенции — консультант
  говорит об этом и предлагает специалиста, а не придумывает факты.
- **Сбор заявки.** ФИО, телефон, компания, согласие; резюме диалога и подобранный продукт
  уходят менеджеру. Заявка сохраняется в SQLite.
- **История сессий.** Сохраняются все диалоги, включая завершившиеся без заявки.
- **Режим отладки.** Время ответа, режим (локальный RAG / LLM / fallback), определённая тема,
  продукт, собранные слоты, модель и использованные документы с оценками.
- **Сброс контекста.** Кнопка «Новый диалог» создаёт новую сессию.
- **Адаптивный интерфейс.** Светлый лендинг в стиле МТС + тёмный чат-виджет; без сборки
  фронтенда и внешних JS-фреймворков.

## Ограничения использования данных

Предоставленные материалы (база знаний, `demo_questions.csv`, `demo_output.csv`,
технический регламент) используются только для выполнения задания. **Не публикуйте
исходные выгрузки и их копии** в открытых репозиториях или общедоступных хранилищах
и не передавайте их третьим лицам. В этом репозитории база знаний включена только
как часть рабочего прототипа; при публикации открытой версии её следует исключить.

API-ключи, токены и другие секреты **не хранятся в коде и репозитории** — все
значения читаются из переменных окружения (см. `.env.example`).

конкурсный `solution.py`. Вложенные пакеты в ZIP-сабмит не переносятся — это требование
регламента.

## Быстрый старт (локально)

Требуется Python 3.11+.

```bash
cd energytool-ai
python -m venv .venv
# Windows: .venv\Scripts\activate
# Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env        # необязательно: без ключей включится демо-режим
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Откройте <http://127.0.0.1:8000/>.

Без `LLM_BASE_URL` и `LLM_API_KEY` приложение работает **офлайн**: BM25-поиск, курируемые
ответы и экстрактивный fallback. Это полноценный демо-режим, а не заглушка.

### Docker

```bash
docker compose up --build
# или
docker build -t energytool-ai .
docker run --rm -p 8000:8000 energytool-ai
```

История сессий в compose хранится в named volume `energytool-storage`
(SQLite-файл `/app/storage/app.db`).

## Подключение LLM

Приложение совместимо с OpenAI-подобным прокси платформы:

```env
LLM_BASE_URL=https://<прокси>/v1
LLM_API_KEY=<ключ>
LLM_MODEL=qwen/qwen3.8-27b
```

- `LLM_MODEL` — генерация ответа и резюме заявки.
- `RERANKER_MODEL` + `USE_RERANKER=1` — необязательный реранкер (`/rerank`).
- При любой ошибке LLM приложение не падает: ответ собирается локальным RAG-fallback.

Секреты читаются только из окружения. В коде и в репозитории их нет.

### Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `LLM_BASE_URL` / `OPENAI_BASE_URL` | — | базовый URL прокси |
| `LLM_API_KEY` / `OPENAI_API_KEY` | — | ключ доступа |
| `LLM_MODEL` / `GEN_MODEL` | `qwen/qwen3.8-27b` | модель генерации |
| `RERANKER_MODEL` | `qwen/qwen3-reranker-8b` | модель реранкера |
| `USE_RERANKER` | `0` | включить реранкер |
| `TOP_K` | `6` | фрагментов базы в контексте |
| `RERANKER_TOP_N` | `4` | сколько оставить после реранка |
| `TEMPERATURE` | `0.1` | температура генерации |
| `MAX_TOKENS` | `900` | лимит ответа LLM |
| `MAX_WORKERS` | `4` | параллелизм `solution.py` |
| `LLM_TIMEOUT` | `45` | таймаут запроса, секунд |
| `KB_PATH` | `data/knowledge-base` | папка базы знаний |
| `DB_PATH` | `data/app.db` | файл SQLite |
| `DATA_DIR` | `data` | входные файлы `solution.py` |

## API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/health` | статус, число фрагментов базы, режим LLM, статистика |
| `POST` | `/api/session/new` | создать новую сессию (сброс контекста) |
| `GET` | `/api/sessions` | последние диалоги |
| `GET` | `/api/sessions/{id}` | сообщения и заявка по диалогу |
| `POST` | `/api/chat` | сообщение пользователя → ответ, источники, debug |
| `POST` | `/api/lead` | сохранить заявку и получить резюме |

Пример:

```bash
curl -s http://127.0.0.1:8000/api/chat \
  -H "Content-Type: application/json" \
  -d '{"message":"У нас старая шиферная крыша. Стоит рассматривать солнечные панели?"}'
```

Ответ содержит `answer`, `sources[]`, `quick_replies[]`, `lead` и `debug`
(`latency_ms`, `mode`, `intent`, `intent_label`, `product`, `slots`).

## Конкурсный `solution.py`

Формат платформы: на входе `questions.csv` и `knowledge-base.zip`, на выходе
`submission.csv` с колонками ровно `id,answer`.

```bash
# DATA_DIR — папка, где лежат questions.csv и knowledge-base.zip
DATA_DIR=/path/to/data python solution.py
```

Что делает:

1. Читает вопросы (UTF-8, поддерживается BOM).
2. Загружает `.md`/`.txt` из ZIP или папки, режет по заголовкам и абзацам.
3. Определяет тему и последнюю реплику (вопросы могут содержать встроенный диалог).
4. Ищет контекст BM25 с синонимами и бонусами профильных документов.
5. При наличии ключей — реранкер и генерация LLM; иначе курируемый/экстрактивный ответ.
6. Пишет `submission.csv` (UTF-8, `QUOTE_ALL`, непустой ответ на каждый ID, ≤ 9 900 символов).
7. Ошибка одного вопроса не роняет весь прогон: используется fallback.

Собрать ZIP для сдачи:

```bash
python scripts/build_submission.py
# → submission.zip: solution.py, answers_core.py, rag_core.py, requirements.txt
```

`requirements.txt` содержит только пакеты из разрешённого набора. В ZIP кладётся
минимальный `requirements-solution.txt` (только `httpx`) под именем `requirements.txt`,
чтобы платформе не пришлось ставить лишнее. `solution.py` в демо-режиме не делает
сетевых вызовов и не требует ключей.

## Как принимаются решения

1. **Интент.** Взвешенные ключевые слова по темам; при неопределённости — общий сценарий.
2. **Слоты.** Регион, тип объекта, мощность, потребление, кровля, приборы, ценовая категория,
   цели, наличие почасовых данных. Числа нормализуются («сорок» → 40), регионы — в читаемые
   названия.
3. **Поиск.** BM25 по контексту диалога + тематические подсказки; профильные документы
   получают бонус, чужие продуктовые документы — штраф. Реранк — по последней реплике.
4. **Ответ.** Курируемое правило (проверенное по базе) → LLM по контексту → экстрактивный
   fallback. В конце — один уместный уточняющий вопрос.
5. **Заявка.** Предлагается, когда собраны ключевые параметры или клиент сам просит
   специалиста. Резюме формируется из слотов и истории, контакты не выдумываются.

### Границы, которые соблюдаются

- Не называются итоговая стоимость, точные сроки, гарантированная экономия, имена клиентов,
  производители оборудования и внутренние алгоритмы.
- Порог оптового рынка — 750 кВт; станции 15–500 кВт; окупаемость 7–9 лет по индикативу
  и 4–6 лет после проработки — только вместе, с оговоркой.
- Сетевая станция без сети не работает; автономность не обещается.
- Старая шиферная кровля (5–10+ лет) — экономически сомнительна без отдельной оценки.
- Персональные данные в платформе учёта и настройка приборов — вне компетенции консультанта.

## Ограничения и развитие

- Демо-режим отвечает курируемыми правилами: он покрывает базу знаний, но не является
  универсальной генеративной моделью. С подключённой LLM ответы становятся свободнее.
- SQLite и один процесс uvicorn достаточны для прототипа; для нагрузки нужны Postgres,
  очередь и внешнее хранилище сессий.
- Дальше: авторизация менеджера, выгрузка заявок в CRM, A/B-оценка ответов, расширение
  базы знаний и автоматическая проверка ответов на запрещённые утверждения.
